# QA Bugs Analytics — Copilot Instructions

## 📋 Project Overview

**Entry Points:**
- **CLI**: `qa-bugs` command → `qa_bugs/cli/cli.py` → `AnalysisService`
- **UI**: `streamlit run src/qa_bugs/ui/app.py` → `AnalysisService` (same backend)

**Main Data Flow:**
```
CSV → Normalizer → apply_filters → metrics compute → ReportBuilder → HTML report
```

**Key Directories:**
- `qa_bugs/cli/` - CLI orchestration and HTML report generation
- `qa_bugs/ui/` - Streamlit web UI (uses same services as CLI)
- `qa_bugs/ingest/` - CSV parsing, field mapping, normalization, filters
- `qa_bugs/metrics/` - All metric implementations
- `qa_bugs/llm/` - Azure OpenAI integration
- `qa_bugs/prompts/` - LLM prompt templates
- `qa_bugs/services/` - Shared service layer (AnalysisService, storage)
- `qa_bugs/report/` - Report building and rendering
- `tests/` - Pytest test suite
- `configs/` - YAML configuration files
- `data/` - Sample CSV files for testing

## 🏗️ Architecture Conventions

### Defect Tracking
When asked to fix a bug/defect, first add an entry to `bugs.md` with a very short description, then make the code fix. Use `bugs.md` as the lightweight defect registry.

### Metrics Contract
Every metric **must** inherit from `Metric` (see `qa_bugs/metrics/base.py`) and return `MetricResult`:
- `.tables`: dict[str, pandas.DataFrame] - All data tables
- `.charts`: dict[str, plotly.graph_objs.Figure] - Plotly figures for visualization
- `.summary`: str - Short human-readable summary
- Use `Metric.payload()` method when passing results to LLM

### Adding New Metrics
1. Create metric class in `qa_bugs/metrics/<metric_name>.py` inheriting from `Metric`
2. Register in `qa_bugs/metrics/__init__.py` in the `METRICS` mapping (e.g., `"metric_id": MetricClass`)
3. Add parameters to `configs/config.yml` under `metrics.params.<metric_id>`
4. Create LLM prompt template in `qa_bugs/prompts/metric/<metric_id>.md` (if using LLM)
5. Add tests in `tests/test_<metric_id>.py`

### Report Table Column Names
When creating tables for reports, use these standard column names (see `qa_bugs/report/builder.py`):
- Age/time: `age_days`, `avg_age`, `median_age`
- Counts: `count`, `opened`, `closed`, `total`
- Categories: `priority`, `status`, `environment`, `category`
- Rates: `rate_percent`, `leakage_rate`, `rejection_rate`

## 📊 Data Ingestion

### Field Normalization
- All CSV field mapping goes through `Normalizer` (`qa_bugs/ingest/normalizer.py`)
- Field mappings defined in config: `fields_mapping` section
- Supports auto-detection via `FieldMappingService` (LLM or fuzzy matching)
- Standard internal field names: `key`, `created_at`, `resolved_at`, `status`, `priority`, `fix_version`, `environment`, `category`

### Data Processing Rules
- Timestamps: coerced with `pd.to_datetime(..., errors='coerce')` - intentional timezone handling
- Environment values: automatically upper-cased by Normalizer
- Status filtering: `exclude_statuses` from `metrics.params.common` (list of statuses to ignore)
- Date ranges: `since` and `until` parameters filter by `created_at`

### Filters
Applied in `qa_bugs/ingest/filters.py`:
- Date range filtering
- Status exclusions
- Per-metric custom filters

## 🤖 LLM Integration

### Configuration
- **Providers**: Supports both Azure OpenAI and direct OpenAI API
- Config section: `llm` in YAML (see `configs/config.yml`)
- Switch providers via `llm.provider` setting: `"azure"` or `"openai"`

**Azure OpenAI:**
- Set `provider: azure` in config
- Credentials from environment: `AZURE_OPENAI_KEY`, `AZURE_OPENAI_ENDPOINT`
- Required fields: `endpoint`, `deployment`, `api_version`
- Example config: `configs/config.yml`

**Direct OpenAI API:**
- Set `provider: openai` in config
- Credential from environment: `OPENAI_API_KEY` (or set `api_key` in config)
- Required field: `model` (e.g., "gpt-4o-mini", "gpt-4o", "gpt-3.5-turbo")
- Example config: `configs/example.openai.config.yml`

**Disable LLM:**
- CLI: `--llm off` flag
- Config: `llm.enabled: false`

### Prompts
- Location: `qa_bugs/prompts/`
- Structure:
  - `prompts/metric/<metric_id>.md` - per-metric analysis
  - `prompts/summary/overall.md` - overall summary
- Placeholders: `{{context_json}}` or `{{metrics_context_json}}` replaced with data
- Context format: CSV or JSON (controlled by `llm.context_format` config)

### Service
- Implementation: `qa_bugs/llm/service.py`
- Debug options: `llm.debug` and `llm.log_prompts` (saves prompt/response to output dir)
- Token limits: `llm.max_tokens`, `llm.max_prompt_chars`, `llm.table_row_limit`

## 🎨 UI (Streamlit)

### Running the UI
```bash
streamlit run src/qa_bugs/ui/app.py
```

### UI Architecture
- Main app: `src/qa_bugs/ui/app.py`
- Components: `src/qa_bugs/ui/components/` (results display, charts, etc.)
- Shares backend: Uses same `AnalysisService` as CLI
- Config: UI allows uploading config YAML or using defaults
- Features:
  - CSV file upload
  - Field mapping (manual or auto-detect)
  - Date range selection
  - Metric selection
  - LLM toggle
  - Results display with tabs (Overview, Charts, Data Tables, LLM Insights)

### UI vs CLI Differences
- UI: interactive web interface, in-memory results, session-based logging
- CLI: command-line, file-based output in `output/run_*/`, persistent reports
- Both: use identical AnalysisService, metrics, and report generation logic

## ⚙️ Configuration

### Config File Structure
See `configs/config.yml` for full reference.

**Key sections:**
- `project`: timezone, general settings
- `fields_mapping`: CSV column → internal field mapping
- `auto_mapping`: LLM-based field detection settings
- `metrics`: enabled metrics list and per-metric parameters
- `llm`: Azure OpenAI configuration

### Common Metric Parameters
- `metrics.params.common.exclude_statuses`: list of statuses to ignore globally
- `metrics.params.<metric_id>`: metric-specific settings (e.g., `open_statuses`, `closed_statuses`, `intended_env`, `leak_envs`)

## 🐛 Troubleshooting

### Common Issues

**Missing LLM credentials:**
- **Azure**: Ensure `.env` file exists with `AZURE_OPENAI_KEY` and `AZURE_OPENAI_ENDPOINT`
- **OpenAI**: Ensure `OPENAI_API_KEY` environment variable is set
- Or set `llm.enabled: false` in config
- Or use `--llm off` flag

**CSV field mapping errors:**
- Check `fields_mapping` in config matches actual CSV headers
- Try auto-detection: `--auto-map` flag or `auto_mapping.enabled: true`
- Verify required fields: `key`, `created_at`, `status`, `priority`

**Timezone issues:**
- Set correct timezone in `project.timezone` config
- Timestamps are coerced with `pd.to_datetime(..., errors='coerce')`
- Check for invalid date formats in CSV

**Metric not found:**
- Verify metric is registered in `qa_bugs/metrics/__init__.py` `METRICS` dict
- Check metric ID matches config and command-line args

**Report rendering issues:**
- Ensure table column names match expectations (see "Report Table Column Names" above)
- Check Plotly figure creation in metric's `.charts` output
- Verify `MetricResult` structure is correct

**Streamlit UI not starting:**
- Ensure Streamlit is installed: `pip install streamlit`
- Check port availability (default: 8501)
- Review logs: `output/<latest_run>/qa_bugs_ui.log`

## 📝 Code Style

### General Rules
- Follow **PEP 8** style guide
- Use **type hints** for function arguments and return values
- Write **clear, maintainable code** with descriptive variable names
- Prefer **config-driven parameters** over hardcoded values
- Add **docstrings** for public functions and classes

### Project-Specific Rules
- All metrics return `MetricResult` (never dict or tuple)
- Configuration read from `metrics.params` in YAML (never hardcoded)
- `intended_env` and `leak_envs` **must be lists** (no string support)
- Field normalization **always** through `Normalizer` (never manual mapping)
- LLM context format: CSV or JSON (controlled by config, CSV is more token-efficient)

- Check if similar feature exists (e.g., other metrics, filters)
